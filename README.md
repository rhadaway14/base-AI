# Architected AI Starter

A reusable, production-shaped starter repository for AI-enabled applications built with **Python/FastAPI**, a **Next.js** frontend, a replaceable LLM provider seam, **Couchbase** integration, Docker, Terraform, and executable architecture guardrails.

This repository is intentionally a **walking skeleton**, not a feature-rich sample application. A fresh project should begin with a small end-to-end path that proves its contracts, configuration, observability, security posture, and deployment shape before domain complexity is added.

## Start a new project

```bash
git clone <your-template-repo> my-project
cd my-project
python scripts/init_project.py \
  --name "My Project" \
  --slug my-project \
  --description "What this project does and for whom."

make install
make check
make up
```

If you host this repository as a **GitHub Template Repository**, use **Use this template** instead of cloning and then run the same initializer.

## What this template preserves

The template is based on the architectural discipline of a larger multi-service AI project:

- **Contracts before implementations.** Shared domain and event contracts sit in reusable packages rather than inside service code.
- **Replaceable provider seams.** Application code depends on protocols; cloud/model SDKs stay behind adapters.
- **Offline-first development.** `LLM_PROVIDER=echo` makes the whole walking skeleton testable without cloud credentials.
- **Truthful capabilities.** The application reports what is actually enabled instead of letting the UI infer it.
- **Configuration fails closed.** Unsafe production combinations are rejected at startup.
- **Architecture is executable.** Important dependency boundaries and invariants have tests.
- **Docs are source.** Architecture, decisions, security, operations, and implementation plans live with the code.
- **One-command quality gates.** Formatting, linting, typing, tests, frontend checks, and security scans are standardized.
- **Production-shaped local development.** Docker Compose mirrors deployable boundaries without requiring the cloud.
- **Infrastructure as code.** Terraform is the default cloud definition; optional Kubernetes guidance is isolated.

See [docs/architecture/principles.md](docs/architecture/principles.md).

## Repository layout

```text
apps/
  api/                 Public API and capability surface
  agent-gateway/       AI/model invocation and event streaming
  web/                 Next.js frontend
packages/
  domain-models/       Shared typed contracts
  llm-client/          LLM protocol, echo adapter, provider factory
  couchbase-client/    Persistence boundary and settings
  observability/       Structured logs and correlation IDs
docs/
  product/             Product brief and scope
  architecture/        System architecture and engineering principles
  decisions/           ADRs
  security/            Threat model and invariants
  operations/          Local development, deployment, runbook
  ai/                  Instructions for ChatGPT/Claude collaboration
infrastructure/
  terraform/           Shared modules + environment roots
  kubernetes/          Optional deployment guidance
observability/         Optional Prometheus/Grafana extension point
prompts/               Version-controlled model prompts
tests/
  unit/ integration/ end-to-end/ architecture/
scripts/               Project initialization and repo checks
```

## Development

```bash
make install          # resolves dependencies; commit the generated uv.lock
make env              # create .env from .env.example
make check            # lint + format check + strict typing + unit/architecture tests
make web-check        # frontend typecheck + lint + build
make up               # start local Couchbase + gateway + API + web
make test-integration # infrastructure-backed tests
make test-e2e         # full-stack acceptance tests
make security         # local secret/dependency checks where tools are installed
```

`make help` lists all targets.

## First-project workflow

1. Run `scripts/init_project.py`.
2. Commit the `uv.lock` generated by the first `make install`; CI can then be changed to `uv sync --frozen`.
3. Fill in `docs/product/project-brief.md` before feature coding.
4. Replace the starter architecture in `docs/architecture/system-architecture.md` with the actual target topology.
5. Record material technology choices as ADRs.
6. Define the first **walking-skeleton acceptance test** in `tests/end-to-end/`.
7. Build the thinnest vertical slice that makes that test pass.
8. Add project-specific security and architecture invariants as tests.
9. Only then expand services, agents, retrieval, queues, or data models.

## AI collaboration

Both ChatGPT and Claude should begin by reading:

1. `AGENTS.md`
2. `docs/product/project-brief.md`
3. `docs/architecture/system-architecture.md`
4. `docs/architecture/principles.md`
5. accepted ADRs under `docs/decisions/`
6. `docs/implementation-plan.md`
7. `docs/ai/session-handoff.md`

`CLAUDE.md` points Claude to the same canonical instructions rather than maintaining a separate set of rules.
